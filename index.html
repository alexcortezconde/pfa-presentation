Prompt Engineering · Techniques

5 Prompt Engineering
Techniques Applied

01 🎭 Role Definition Defined the agent as a personal finance classifier specialized in Mexican banking notifications
02 📋 Structured Output Strict JSON schema with 7 typed fields — enabling automated routing in Maestro without parsing
03 📝 Few-Shot Examples Real email bodies paired with expected JSON responses — teaching the agent by example, not just by rules
04 ⚙️ Field-Level Specifications Detailed rules per JSON field — explicit merchant lists, category distinctions, and critical edge cases like gas types
05 👤 User Profile for Anomaly Detection Defined typical spending patterns so the agent flags cosmetics and unfamiliar merchants as possible card lending
Technique 4 · Field-Level Specifications — actual prompt text
-- CRITICAL DISTINCTION - GAS TYPES: ----------------------------------------
- Vehicle fuel:  SERV RUDIGAS, PEMEX, BP, SHELL, OXXO GAS     → Transportation
- Domestic gas:  TOLUGAS, GAS IMPERIAL, ZETA GAS, GASMART     → Home
These are completely different categories. Never confuse them.

Real-World Use Cases

Real-World Scenarios

CASE 01 Standard Card Purchase Flow 1 · Normal Transaction A purchase notification arrives. The Classifier identifies it as a normal transaction. The Robot registers it automatically in Sheets. No human intervention required.
CASE 02 Family Member Borrows Card Flow 1 + Flow 2 A family member makes an online purchase with my card. The email arrives, I confirm it as a loan via Action Center. It's logged in both Transactions and Loans. 15 days later, they send a payment screenshot via Telegram — it's processed automatically and the outstanding balance is updated.
CASE 03 Partial Loan Repayment Flow 1 + Flow 2 A family member uses my card at a local business. I confirm the loan via Action Center and it's registered. Later, they forward a Telegram payment screenshot — the system matches it, applies the partial payment, and clears the remaining balance.
CASE 04 Unregistered Incoming Transfer Flow 2 · Unregistered Someone sends money and forwards the transfer screenshot via Telegram, but the loan wasn't previously registered. It reaches Action Center for review — I confirm it's a repayment and it's manually logged in the spreadsheet.
CASE 05 Suspicious Charge Flow 1 · Fraud Path A unusual charge notification arrives. The Classifier flags it as Unusual, routes it to Action Center. I confirm it's suspicious and a Jira ticket is created automatically for follow-up.
CASE 06 Non-Financial Email Flow 1 · Not Financial A marketing email, newsletter, or promotion arrives. The Classifier detects it contains no financial or banking content. The flow ends immediately — no registration, no action taken.

Retrospective

Challenges &
Lessons Learned

⚡ 01 Robot Units Limit Community Plan: 300 runs/month. Forced efficient testing and smart debugging strategies. Design for minimal robot execution. Let agents handle logic — robots handle I/O only.
🔄 02 Variable Types Objects vs Strings between Maestro components caused silent failures mid-flow. Always validate data types at every Maestro boundary. Log every input and output.
🤖 03 Telegram → Google Integration Built a Python bot that receives bank screenshots via Telegram and automatically forwards them to Gmail and saves them to Google Drive. Python + Telegram Bot API + Gmail API + Google Drive API — wired together in under 100 lines. No UiPath needed for this layer
🔁 04 Prompt Iteration Prompts are never "done". Each new email format reveals new edge cases and failures. Evaluation sets catch regressions. Treat prompts like code — version and test them.
📊 05 Sheets as Database Works for MVP. No RBAC, limited queries, concurrency risks at any real scale. Production needs SQL or SharePoint. Sheets was the right call for rapid iteration.
